# Artifact classes: what ships and what is strippable

Every file in this repository declares one of two classes, so a release
distribution can be reduced to the files a trainee actually needs without anyone
deciding file by file:

| Class | Meaning |
|---|---|
| `production` | Ships. The simulator does not run, or does not carry its own provenance, without it. |
| `dev` | Exists to build, test or document the simulator. Removable from a distribution. |

Anthony, 2026-08-30, setting this convention: *"make sure all production files are
tagged so they can be removed later such as dev files and build documents.
changelog stays canonical."* `CHANGELOG.md` is therefore `production` — it is the
project's record of record, not a build document, and is never stripped.

## The marker

The marker in each file is the single source of truth. Nothing else — no manifest
list, no directory rule — decides a file's class, so the classification cannot
drift from the files it describes.

Put it in the **first three lines**, in that file's comment syntax:

```
// @artifact production     .js
# @artifact dev             .py, .sh (after the shebang), .gitignore
<!-- @artifact dev -->      .md, .dc.html (after the doctype)
```

Exactly one marker per file. A new file with no marker fails
`tests/artifact-classes.test.js`, which is the point.

## The four files that carry no marker

These are classified in `tests/artifact-classes.test.js` and in
`tools/strip-dev.sh`, and nowhere else. Keep the two lists in step.

| File | Class | Why it carries no marker |
|---|---|---|
| `support.js` | production | Generated dc runtime; `UPGRADE-PLAN.md` rule 2 forbids editing it. |
| `dist/experion-station-sim-standalone.html` | production | Generated by `tools/build-dist.py`; rule 2 forbids hand-editing. |
| `LICENSE` | production | Legal text, kept verbatim. |
| `.thumbnail` | dev | Binary WebP export artifact; neither build references it. |

## Boundary calls, and the reasoning

- **`docs/RESOURCES.md` is `production`.** It is not a build document. It is the
  provenance register that rules 1 and 6 depend on, and `src/` code comments cite
  it by section (`// ISA-18.2 state model ... (RESOURCES 2.5)`). Shipping the code
  while stripping the register it cites would leave the citations dangling and the
  IP boundary undocumented. When `docs/SOURCE-PROVENANCE.md` arrives in v3 stage
  S5 it is `production` for the same reason.
- **`docs/dev/` is `dev` in full.** `CODE-MAP.md`, `UPGRADE-PLAN.md` and
  `V3-PLAN.md` are addressed to whoever builds the simulator, not to whoever
  trains on it.
- **`src/` is `production` in full.** Both builds load these modules; the
  standalone inlines them.
- **`.gitignore` is `dev`.** A distribution is not a git checkout.

## Using it

```bash
tools/strip-dev.sh                # dry run: list what would go, what would stay
tools/strip-dev.sh --out /tmp/rel # copy the production tree elsewhere, repo untouched
tools/strip-dev.sh --apply        # remove dev files in place (refuses on a dirty tree)
```

`--apply` is recoverable with `git checkout .`. The script refuses to run at all
if any tracked file is unclassified, so a stripped tree is never the result of a
file quietly falling through.

## What the test guarantees

`tests/artifact-classes.test.js` asserts that every tracked file declares a class,
that `tests/`, `tools/` and `docs/dev/` are wholly `dev`, that the shipping
artifacts and all of `src/` are `production`, that `CHANGELOG.md` is `production`,
and — the property that makes stripping safe rather than hopeful — that **no file
either build loads is `dev`**, checked by re-reading the app's own
`<script src="./...">` tags rather than by trusting this document.
